## Immutable design decisions

- **DD-1** Protocol tier is **Compact on Midnight (0.31.x / ledger 8)**, not EVM.
- **DD-2** **Base is read-only**; no contracts deployed there in v1.
- **DD-3** Indexed Merkle tree **depth 16** per pool; address-sorted; leaf points
  to `next_addr` for non-membership.
- **DD-4** Amounts are **unsigned `bigint`**; signed quantities are `{in,out}` pairs.
- **DD-5** Determinism is a hard invariant — byte-identical roots are testable.
- **DD-6** Wallet ownership verified **off-chain by the client** in v1 (ledger-9
  in-circuit check deferred).
- **DD-7** Bonds are **mandatory shielded USDM on Midnight** (v1); cross-chain
  slashing deferred.
- **DD-8** (resolved 2026-10-20) Hash primitive injected behind the `Hasher`
  interface. `persistentHash` is SHA-256 by definition (over Compact's byte
  serialization: Uint LE, Bool 1 byte, Bytes raw), so it was never a placeholder
  to "fill in". **Merkle trees the circuit verifies now use `transientHash`**
  (Poseidon, Field digests): `PoseidonHasher` in `@mmr/merkle/poseidon`, exact by
  construction (it calls compact-runtime's `transientHash` over the circuit's own
  types) and KAT-checked against the compiled `proveEpoch`. **Commitments that
  are ledger state stay on `persistentHash` / `persistentCommit`** (C2 wallet /
  terms, `epochKey`), reproduced by `CompactHasher`. `Sha256Hasher` (tagged) is
  off-circuit only. Caveat: the runtime documents `transientHash` as "not
  guaranteed to persist between upgrades". Roots are re-derivable from published
  trees, but a Midnight upgrade that changes Poseidon would require re-rooting
  in-flight epochs. Pin the toolchain and re-run the KAT on every upgrade.

- **DD-10** `rootOfRoots` stays **`Bytes<32>`** in the public `proveEpoch`
  interface (not `Field`). The circuit computes the root as a Field and casts it
  once (`h10 as Bytes<32>`, little-endian; Field→Bytes is injective, so the
  comparison is exact). Chosen because the TS caller, the attester-signed
  manifest (`rootOfRootsHex`), and `registration.activate` already carry 32-byte
  roots; `RootOfRoots.root` passes straight through. Cost: one 255-bit
  decomposition per proof. The other direction (`Bytes<32> as Field`) was avoided
  because it can fail on values ≥ the modulus at the public boundary.

- **DD-9** (C2) The terms commitment is `persistentCommit<Terms>(terms, termsSalt)`
  over the **structured** `Terms`, in both `registration.register` and
  `proveEpoch` (struct kept identical in both files; KAT-checked). Chosen over
  keeping the opaque `persistentHash(termsPreimage)`, which would have needed a
  second proof that the struct matches the preimage for no benefit. Salted (not
  a bare `persistentHash<Terms>`) because terms are low-entropy and a bare hash
  could be brute-forced from the public ledger.

- **DD-11** (M2) `from_treasury` is a **subset of `xfer_in`** (the loan is one of
  the transfers in), so I5 excludes it: `xfer_out + from_treasury ≤ xfer_in + D`
  (underflow-safe form of `xfer_out ≤ xfer_in − from_treasury + D`, INVARIANTS.md
  I5). Corrects the prior `+ from_treasury`, which granted outflow budget equal to
  the loan (a rug of the loaned assets passed I5). The indexer's real Base reader
  MUST populate `xfer_in` to include treasury inflows for this to hold; fixtures
  updated to match. D is a **lifetime** budget enforced cumulatively by the
  carry-forward commitment, not per-epoch.

- **DD-12** (H4) The claim verifies what it credits against the on-chain
  `epochUptime` record. **A1:** an epoch "passed" uptime when its recorded
  bucket count ≥ a committed **`minUptimeBuckets`** term (a bucket count, not a
  percentage — the record is a bucket count and the oracle already models this as
  `minUptimeBuckets`; no in-circuit division). **B1:** `epochsPassed` is counted
  over epochs `1..epochsTotal` where **`epochsTotal`** is the committed contract
  length, so a failed or unproven epoch (no qualifying record) counts toward the
  total but never toward passed, and passed can never exceed total. Chosen over a
  separate on-chain "settled epochs" counter (B2), which would need to record
  failed-but-settled epochs that `proveEpoch` can't (it reverts on failure).
  Adding these two terms is **atomic with the circuit** (commitTerms, the circuit
  `Terms` struct, registration, and the KAT move together, per DD-9), so the TS
  half takes them as explicit parameters until that change lands.

- **DD-13** (H1) The depth_root band leaf is a **dense** fixed 48-bucket
  `BandSeries { band_bps: Uint<64>, bid: Vector<48, Uint<128>>, ask: Vector<48,
  Uint<128>> }` (missing bucket = 0), hashed with **`transientHash`**
  (`PoseidonHasher`), in a band tree of **fixed depth 2** (≤ 4 bands, padded with
  an empty band-0 leaf). Chosen over the sparse `encodeBandSeries` because
  `PoseidonHasher` can only hash fixed Compact struct layouts and dense maps
  straight onto the `bidMin`/`askMin` `Vector<48>` witness; sparse and dense
  forms of the same values give the same leaf and the same uptime. Supersedes
  the earlier note that the band tree could stay `Sha256Hasher`: everything the
  circuit verifies is Poseidon. The opened leaf carries `t.band_bps`, so only
  the contracted band opens; its index is not checked. Proving requires
  `bucketsPerEpoch == 48` and ≤ 4 bands (`DEFAULT_CONFIG`). The flow
  commitment is settled by DD-14.

- **DD-14** (M1) `flow_root` is `transientHash<FlowSeries { buy: Vector<48,
  Uint<128>>, sell: Vector<48, Uint<128>> }>` — the hash of the wallet's WHOLE
  dense per-window series (window = 30-min bucket index, 0 = no trade), with no
  per-window tree. The circuit rebuilds it from the full witness, so every window
  is in the I7 sum. Chosen over per-window leaves + paths (the TS-half spec):
  there the prover picks which windows to open and can omit round-trip-heavy
  ones, and aggregating arbitrary window ids across 16 slots in-circuit is
  costly. Windows outside [0, 48) cannot be committed (the indexer throws); the
  oracle, which aggregates any window id, agrees on every committable input.

- **DD-15** (H4) `claim` lives in `epoch_proof.compact` (Compact contracts cannot
  read another contract's ledger) and verifies epochs by **private Merkle
  membership**, not by looking up `epochUptime[H(id, e)]` — that lookup would
  disclose the engagement id and link the MM's profile to the engagement,
  defeating I10's unlinkability. `proveEpoch` appends `EpochRecord { id, epoch,
  uptime, termsCommit }` to `HistoricMerkleTree<20>` `epochRecords` (all fields
  already public); `claim` proves each presented record against a historic root,
  doing the ledger check for all `MAX_EPOCHS = 90` slots unconditionally (absent
  slots reuse the constructor's genesis-record path) so nothing about which
  epochs exist leaks. `termsCommit` in the record binds the threshold and contract
  length to the accepted terms. An MM may withhold a record (only lowering its own
  count) but cannot add one. Claim requires `persistentHash(secret) ==
  engagementId`. Tree depth 20 (~1M records) and 90 slots are the claim circuit's
  size drivers.

- **DD-16** (M3) A defaulted engagement's bond goes to a **beneficiary key fixed
  at `postBond`** (the client — the harmed party), so the MM cannot redirect it
  later. The spec did not name a slash destination; burning
  (`shieldedBurnAddress()`) or a protocol treasury are one-line alternatives.
  Custody makes the bond value public (a contract can only hold a coin it can
  see); the MM's treasury source stays shielded.

- **DD-17** (H3b) **One contract.** Registration and the bond moved into
  `epoch_proof.compact` (after DD-15 did the same for `claim`): Compact 0.31.1
  rejects cross-contract calls, and a gate is only sound if it reads its anchor
  from its own ledger. Chosen over keeping `bond` separate with its own anchors,
  where a settle step could not check that the epoch was proven (an MM could
  "settle" unproven epochs and release the bond), and over merging only
  registration + bond (same flaw). Anchors are written once, bounded to the
  recording block's time (600 s tolerance), and every gate reads them back.
  Default deadlines use the latest possible root publication (epoch end +
  attester timeout), since root publication is not on-chain yet — the most
  lenient anchor for the MM. Cost: the ledger layout change regenerates
  proveEpoch/claim keys once (same k).

- **DD-18** (M3b) **Bond release schedule:** one tranche per **settled** epoch
  (settled = proven under the registered terms, H3b), paid to the bond owner;
  after k released epochs of E, the cumulative release is exactly ⌊B·k/E⌋ (B =
  the posted bond, E = the committed `epochs_total`). Exact rather than "at most",
  so the last epoch carries the remainder and the tranches sum to B with nothing
  stranded in escrow. Uptime does not gate a tranche: the bond secures *honest
  delivery* (I1–I5, I7 hold, or proveEpoch reverts); the uptime KPI goes to the
  public record via `claim`. An epoch that is never settled is defaultable (the
  whole remaining bond is slashed, DD-16). Cost: E becomes public at registration
  (`contractEpochs`) — the tranche size reveals it at the first release anyway,
  since the bond value is public (DD-16), and an engagement's duration is visible
  from its settlements. Chosen over a time-based vesting (would release on time
  passing, not on proofs) and over B/E per epoch with a final sweep (needs a
  separate remainder rule).
- **DD-19** (Unit 3 / 2a) **Price orientation + scale:** a pool's **base** token is
  the one that is not in the chain's ranked quote-asset list (`ChainConfig.quoteAssets`:
  Base USDC > USDbC > WETH; Ethereum USDC > USDT > WETH); if both are quote assets,
  the higher-ranked one is the quote; a pool with no quote asset is not priced.
  `PriceSample.price` (and the manifest's `referencePrice`) is **raw quote units per
  raw base unit, Q96** (× 2^96, floor), exact in bigint from `slot0.sqrtPriceX96` —
  no float, no `decimals()`. Engagement-agnostic and fixed per chain, since it feeds
  signed data. Chosen over token0-as-base (arbitrary: a client token sorts either
  side of USDC) and over an unscaled integer (truncates to 0: USDC per wei of WETH ≈
  2.4e-9). Note it is the *inverse* sense of the oracle's `P` (base per quote) —
  nothing compares the two today; a consumer that does must convert.
- **DD-20** (Unit 3) **TWAP sampling:** the reference price is the winsorized TWAP
  of spot prices sampled every `priceSampleSeconds` (config, default **60 s**)
  across `[endTs − twapWindowSeconds, endTs]`, endTs included (31 samples at the
  defaults); each sample is `slot0` at the last in-range block with timestamp ≤ the
  sample time (DD-19). The schedule is derived from config by `buildEpoch` and
  passed to the provider, and the three parameters are written into the manifest,
  so `referencePrice` is byte-recomputable. Replaces bucket-boundary sampling, which
  left 2 samples in a 30-min window (the last with zero weight): the "TWAP" was one
  spot read, settable by one block, and winsorization trimmed nothing. Now
  k = ⌊31 · 0.05⌋ = 1 sample is trimmed per tail. Cost ≈ 110 RPC calls per pool per
  epoch on Base.
- **DD-21** (Unit 3 / 2b) **Pool discovery = pair enumeration, not a log scan.**
  The indexed pool set is every Uniswap v3 pool of a configured **base token**
  (`IndexerConfig.baseTokens`) against each of the chain's quote assets (DD-19), at
  each fee tier, read with `factory.getPool` at the epoch's end block via Multicall3
  and cross-checked against its CREATE2 address; kept if initialized and
  `liquidity() ≥ liquidityFloor`. Deterministic from (config, end block), costs 2
  `eth_call`s, and needs no `eth_getLogs` (the Free-tier key allows 10-block ranges
  only). Chosen over a full `PoolCreated` scan (needs a paid key; indexes every
  pool on the chain, which the protocol never uses) and over a second RPC provider.
  Consequence: the indexer covers the tokens of its engagements, and adding a
  client means adding its token to `baseTokens` (recorded in the manifest).
  **Open:** `liquidityFloor` compares raw `liquidity()` (√(x·y) in raw units),
  which is not comparable across pools with different decimals — a floor
  meaningful across pools needs a quote-denominated depth measure (do with 2c's
  depth math).
- **DD-22** (Unit 3 / 2c) **Swap attribution = net token flow.** In every tx in
  which the pool emits a Swap, each address's swap flow is its **net** base and quote
  delta over all of the tx's base/quote Transfers (from the receipt); routers and
  executors net to zero and the pool (the counterparty) is excluded. `swapBaseIn/Out`
  / `swapQuoteIn/Out` are those nets; the flow window is the bucket of the tx's
  block. Other base Transfers are pool legs (pool counterparty: LP, fees, flash) or
  transfers (`xferIn/Out`, base only). Evidence (status log 2026-10-22): real MM
  inventory is a contract driven by many signer EOAs that hold nothing, often via an
  executor — `tx.from` names the right address 5/46 times, `Swap.sender` 10/46,
  `Swap.recipient` 44/46 (and credits a payer's sale to the recipient on
  swap-and-send). Known limits: a native-ETH leg is invisible (no Transfer); a plain
  transfer inside a swap tx counts as swap flow (base out without quote in still
  counts as net selling under I4).
- **DD-23** (Unit 3 / 2c) **Depth is quote-denominated, and so is the pool floor.**
  For band b around the current price: `minBid` = quote a position holds between the
  price and the price where the base is b lower; `minAsk` = quote it takes to buy
  the position's base up to the price where the base is b higher (L·Δ√P in quote,
  before fees). Both are raw quote units, so I6's single target δ* is meaningful on
  both sides (the original plan had bid in quote and ask in base). Per-wallet bucket
  depth is the minimum over the bucket of the sum over its positions, evaluated at
  the bucket's start state and after every block with an event (exact, no per-block
  reads). The pool floor replaces raw `liquidity()` with QuoterV2-measured
  min(bid, ask-net-of-fee) at `poolDepthFloor.bandBps`, compared with a floor **per
  quote asset** — so pools are compared only in their own quote's units (resolves
  DD-21's open point). Fees and uncollected `tokensOwed` are excluded from lpBase/lpQuote.
- **DD-24** (Unit 3 / 2c) **LP positions = position registry + ownership rule.**
  Passive LPs emit no events, so depth cannot come from the epoch's activity set:
  every position-manager NFT's static pool/ticks are kept in a registry built by one
  state scan of `positions(id)` over all ids (Base: 6.32M, ≈ 10–11 h once on the
  Free tier), cached and extended per epoch from the last id; owner and liquidity
  are read at both ends of the epoch. Credit goes to the owner at the end if it also
  held the NFT at the start or the NFT was minted this epoch, to the owner at the
  start if it was burned this epoch; an NFT that changed hands mid-epoch earns no
  depth that epoch (no one can rent depth by moving NFTs). Direct (non-NFT) pool
  positions are tracked when touched in the epoch (Mint/Burn); a direct position
  untouched all epoch is invisible until a paid key allows a Mint-history scan.
  Every NFT owner with a credited position becomes a leaf, so a passive MM is scored.
- **DD-25** (Unit 3) **Bounded position discovery from a pool's Mint history.** On
  the Free tier the global registry (DD-24) costs ≈ 10–11 h once on Base, so a pool
  may instead be indexed from its creation block: scan pool Mint + position-manager
  IncreaseLiquidity from creation to the epoch start (plus the epoch's own logs);
  an NFT is the pool's when its IncreaseLiquidity shares a tx with a manager-owned
  pool Mint and `positions(id)` confirms the pool key; every other Mint owner is a
  direct position. Complete (NFT and direct) and recomputable; cost grows with the
  pool's age (≈ 1 request per 10 blocks of history), so it suits recently created
  pools. Chosen by the user for the Unit 3 milestone; the registry stays for older
  pools / a paid key.
- **DD-26** (I8) **Attester-root registry = Option B, sound variant.** The committee
  is three `attesterId(secret)` values fixed by the constructor (2-of-3). Each member
  submits `publishRoot(epoch, root, cid)` in its own transaction, authenticated by
  proving knowledge of its secret — **not** `ownPublicKey()`, which the prover chooses
  (I9). One vote per member per epoch over the exact (root, cid); the root is
  published when two members agree. `proveEpoch` binds `rootOfRoots` to
  `publishedRoot[epoch]` (a settle-only gate would let a proof against a self-made
  root settle); `settleEpoch` needs the root published; a never-published epoch is
  never defaultable (product spec: void, no penalty). The off-chain committee holds
  secrets and submits; counting is on-chain only. Open: `publishedRoot` uses the
  contract's (engagement) epoch number; aligning it with indexer epochs is a deploy
  item.
- **DD-27** (funding) **The loan is proven landed before anything settles.**
  `proveFunding` opens the engagement's wallets against epoch 1's published root
  (I8), with `proveEpoch`'s openings (one shared `openSlotLeaves` circuit) and the
  registration binding (C2), and requires Σ `from_treasury` over member slots ≥
  `loan_L0`, once per engagement; `settleEpoch` requires it. A separate circuit
  because the evidence (epoch-1 indexed data) exists only after activation.

- **DD-28** (identity) **Wallet sign-in is SIWE with an identity wallet, never a
  quoting wallet.** EIP-4361 on Ethereum/Base; EOA signatures verified locally,
  smart wallets via ERC-1271/6492. Signed httpOnly session (HS256, `SESSION_SECRET`).
  Linking a quoting wallet to an account would hand our server the very mapping the
  privacy model keeps on the MM's machine.
- **DD-29** (backend) **The backend coordinates; it never holds the books.** Postgres
  stores accounts, the engagement registry (ids, parties, public commitment, status)
  and read models; client-visible figures are relayed as ciphertext encrypted MM →
  client. 0G and hosted GraphQL indexers were evaluated and kept off the proof path
  (see architecture.md "Backend plan").

- **DD-30** (registration) **No registration without a saved engagement file, and no
  acceptance without checked terms.** The register step computes the protocol's real
  commitments in the browser and refuses to register until the MM has saved the
  passphrase-encrypted file of secrets (losing it makes the engagement unprovable). The
  client receives the full opening sealed to a wallet-derived inbox key, recomputes both
  commitments before Accept unlocks, and accepts by wallet signature (kept as evidence).
  Inbox keys need repeatable signatures (standard EOAs); the app detects and says so
  otherwise. **Units (checked against the circuit, 2026-11-17):** I3/I4/I5 and the
  DD-27 funding check compare loan L0, outflow cap D and net-selling cap S with the
  client token's raw balances/transfers/swaps, so they are in **base-token** raw units;
  depth target (I6, DD-23) and Q0 are **quote-token** raw units; P converts raw quote
  to raw base (P = 10^(baseDec−quoteDec) / price, rounded down so held quote never
  counts for more than it's worth). The wizard previously treated all amounts as
  6-decimal USDM — fixed: it now uses the pool's base/quote tokens and decimals, and
  the file records them. **Protocol limit found:** P is a whole number, so pools where
  one raw quote unit is worth less than one raw base unit (e.g. cbBTC/USDC: 10^2/95,000
  < 1) can't express a floor price; the wizard refuses one there and explains (blank =
  sold tokens don't count). A fixed-point P needs a circuit change before such pools
  get a floor price.

- **DD-31** (indexer) **Time-based parameters must be in seconds, not blocks.** Base moved
  from 2 s to 0.2 s blocks around 2026-11-05/06 (measured: 2.000 s/block before, 0.200 s
  after). `kMinBlocks = 30` (anti-JIT: positions alive fewer blocks get no depth credit)
  silently went from 60 s to 6 s, ten times weaker. **Resolved (2026-11-17):**
  `kMinSeconds = 60` replaces `kMinBlocks`; the provider reports `lpFirstActiveTs` (the
  block timestamp, not the number) and a position is JIT iff `endTs − lpFirstActiveTs <
  kMinSeconds`. On 2 s blocks this is exactly the old 30-block rule (tested block by
  block), so pre-switch roots are unchanged without a version switch; `kMinSeconds` is now
  in the epoch manifest (it was missing, so the manifest alone could not recompute which
  depth series earn credit). Other block counts: finality is by the RPC `finalized` tag
  and epoch ranges by timestamp, so no other parameter depends on block time.
  Also: a post-switch day is ~432k blocks, 10× the archive-RPC requests per epoch.
- **DD-32** (indexer) **Index epochs are UTC days, numbered by unix day** (`startTs /
  86400`): global, deterministic, independent of any engagement. The daily indexer
  (`apps/worker`; Trigger.dev in production, GitHub Actions for the demo) indexes the last
  closed day per covered chain at 01:10 UTC,
  runs the pipeline twice (first pass publishes to IPFS, second recomputes from the RPC
  cache), requires identical roots, and stores `indexed_epoch` (root, manifest CID, end
  block + hash, manifest). A second write for a (chain, day) with a different root is a
  hard error. Coverage (base tokens per chain) is public config (`MMR_COVERAGE_<chainId>`),
  not engagement data. The position registry (DD-24) persists in `worker_state` between
  runs. Mapping engagement epoch *n* to a day (activation day + n − 1) is part of the
  DD-26 deploy item.
- **DD-33** (infra) **Production runs background jobs on Trigger.dev; this demo runs the
  daily indexer on GitHub Actions' scheduler.** Both run the same `indexDay`
  (`apps/worker/src/trigger/indexer.ts` for Trigger.dev, `apps/worker/src/run-daily.ts` +
  `.github/workflows/daily-index.yml` for the demo), always outside HTTP handlers
  (invariant #1). The job is re-runnable: stored days are skipped, the position registry
  lives in Postgres, and each run re-checks the last `MMR_CATCHUP_DAYS` (3) days.
- **DD-34** (toolchain) **Ledger 9: Compact toolchain 0.36.1, runtime 0.21.0.** Midnight moved
  every network to ledger 9 (Preview relaunched as a new chain on 2026-11-07), so new
  deploys need toolchain 0.36.x. The contract compiles unchanged apart from
  `pragma language_version 0.28.0`; all 11 circuits build and the compiler now emits
  `contract-manifest.json`. Runtime 0.21 renamed the casts (`Field as Bytes<32>` →
  `convertBigintToBytes`; `Bytes<32> as Field` → range-checked `convertBytesToUint`
  bounded by `MAX_FIELD`), made `initialState` and circuits async, and moved query and
  zswap state under `context.callContext` with block time set by `createCircuitContext({ time })`.
  Hashes are unchanged: the pinned Base and Ethereum epoch roots still recompute byte for
  byte. CI installs the checksum-pinned compiler and compiles the contract, so all 123
  contract KATs run there (`KAT_REQUIRE_BUILD=1` fails the run if the build is missing).
  `@mmr/dapp` moves to Midnight.js 5 with the redeploy.
- **DD-35** (contract) **Review fixes: roots by (chain, day), bond and tier rules, a real
  dispute, fixed length.** (1) Published roots are keyed by `rootKey(chain, day)`; `activate`
  records `startDay` (the UTC day after activation, range-checked against the
  block-time-checked `activatedTs`), epoch e is day `startDay + e - 1` and ends at
  `(startDay + e) · 86400`, so engagements that start on different days prove against their
  own day's root and Base/Ethereum roots never collide. (2) `register` fixes tier (1 A,
  2 B, 3 C), chain (1 or 8453), the required bond and the beneficiary publicly, with a fixed
  per-tier minimum bond (A 10,000 / B 5,000 / C 2,500 in the bond token); the bond token is
  a deploy-time constant; `postBond` checks token and amount; `activate` needs the
  engagement secret (only the MM starts the clock) and a posted bond. These values are
  public, not in the committed terms: the bond and beneficiary were already public once
  posted, the client checks them before accepting, and the terms commitment and every TS
  encoder of it stay unchanged. (3) `disputeRoot(chain, day)`: committee members vote; at
  2 of 3 the root is disputed and no epoch on it settles, releases or defaults (the MM is
  not slashed for a bad root; its tranche for that day stays escrowed). The client UI asks
  the committee to recheck instead of offering a bond-backed challenge. (4) Engagements run
  exactly 30 epochs (register and claim), so length links nothing; `claim` loops 30 slots,
  checks the claimed tier against each presented record's tier (`EpochRecord.tier`, written
  by `proveEpoch` from the registered tier) and keeps counters per (profile, tier). A claim
  presenting no records cannot have its tier verified; it only adds misses to that tier.
  Removed `assertNotIdentity`: a `ZswapCoinPublicKey` is a SHA-256 hash of the coin secret
  key (no curve point), and the check was unused; the beneficiary must instead be non-zero.
  Not done: weekly claim batching (claim timing can still correlate with an engagement's end).
- **DD-36** (deploy) **Preview deploy on the ledger-9 SDKs, with a test bond token.**
  `@mmr/dapp` runs on Midnight.js 5.0.1 and wallet SDK 2.0.1: the wallet starts from seeds
  derived from `DEPLOY_SEED`, transactions cross between Midnight.js and the wallet as
  bytes (each decodes with its own ledger copy), and the providers carry
  `config: { networkId, ttlSeconds }`. Preview's faucet hands out unshielded tNIGHT only,
  while a bond is a shielded coin, so `test_bond_token.compact` (Preview scaffolding:
  anyone can mint) is deployed first and `epoch_proof`'s bond token is its color,
  `rawTokenType(pad(32, "mmr:bond:test"), tokenAddress)`; a production deploy names a real
  shielded token instead. The demo committee's three secrets are derived from the deploy
  seed (`sha256("mmr:attester:secret:v1" || seed || i)`); the earlier scripts used fixed
  bytes anyone could reproduce, which on a public chain would let anyone publish or dispute
  roots. In production each attester holds its own key. Proof server 9.0.0; full keys from
  `pnpm --filter @mmr/contracts compact:build` (about 4 minutes, 1.1 GB).
  Deploy is batched (Midnight's batched-deploy runbook): the full deploy writes 39,464 bytes
  (79% of a block; one transaction may use ~65%), so `deploy` sends the constructor state
  with 7 circuits' keys (54%) and adds the other 5 with `submitInsertVerifierKeyTx`, storing
  the maintenance key before submitting and recording each step so a re-run resumes.
- **DD-37** (contract, pipeline) **Funding from registration day, owner-only bond, final days,
  credited claims; proofs from published data.** From the second external review.
  (1) `proveFunding(id, day, root)` accepts the published, undisputed root of any day from the
  registration day through day 1: a loan that lands on the day of registration or activation
  was otherwise unprovable and the market maker would be slashed. (2) `postBond` requires the
  engagement secret, like `activate`: the bond's owner receives every tranche. (3) Disputes
  count until the day's deadline (end + 66 h, the grace deadline of every epoch on that day);
  after it each day is final: settled (released, credited), disputed (neutral: released to the
  market maker, never credited, never defaultable) or neither (defaultable). Releases open at
  that deadline, so the 12-hour challenge after settlement is gone. (4) `settleEpoch` keeps the
  record it settled with; `releaseEpoch` credits it to `creditedRecords` only when the root
  stood, and `claim` reads only that tree (the claim still never reveals its engagement), and
  must present at least one day. Pipeline: the indexer publishes each pool's committed series
  next to its tree (roots unchanged), so the market maker's witness comes from public data
  alone and anyone can check every leaf's depth and flow roots; attesters recompute each day
  from IPFS before voting and dispute a published root that does not recompute. The open point
  found here (the pool was not committed) is closed by DD-38.
- **DD-38** (contract) **The engagement's pool is committed with the terms.** `Terms` ends with
  `pool: Uint<160>`; `proveEpoch` and `proveFunding` assert the opened pool entry is that pool.
  Before, a market maker could prove on any pool in the day's root (another fee tier, another
  covered token). The pool stays private (inside `termsCommit`); the contract, `@mmr/prover`
  and `@mmr/engagement-file` encode it identically (20 bytes, little-endian), and the wizard
  commits the pool it registers. Done before the real-data engagement registered, so no live
  engagement was lost to the redeploy.
